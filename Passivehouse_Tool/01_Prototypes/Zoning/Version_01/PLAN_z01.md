## 0. 读完 Version_06 之后，与本轮有关的现状

- `wwr-tool.html` 1477 行，其中 12 行是气候数据（约 400 KB，占文件 90%）。计算和界面写在同一个立即执行函数里，外部只能拿到 `wwrSelfTest`、`wwrSetConfig` 和自检导出的 `window.__digest / __ui / __suit`。
- **每个立面一组参数**：`S.f[k] = {wwr, n, oh}`（窗墙比、每层窗数、挑檐），窗台高 `S.sill`、窗头高 `S.head` 四面共用。`calc(k)` 从窗墙比反推"n 扇等大的窗"：窗高 `hw = head − sill`，总窗宽 `totW = wwr·len·H / hw`（超过墙长 90% 时悄悄截断），单窗宽 `wi = totW / n`。平面图把 n 扇窗**均匀**画在立面上：第 i 扇中心在 `(i + 0.5) / n × 墙长`。
- `calc(k)` 内部还有两处悄悄修正：窗头高截到吊顶（层高 − 0.3 m），窗台高截到窗头以下 0.4 m（最小窗高 0.4 m）。
- 结果字段（每立面）：窗面积 `AwT`、玻璃面积 `AgT`、实际窗墙比 `wwrAct`、整窗 U 值 `Uw`、冬季得热 `Qgain`、热损失 `Qloss`、净得热 `net / netPer`、高温时段透入辐射 `Qhot / hotPer`、逐小时模拟的过热频率 `ovh / h25`、采光系数 `DF`、以及只用于表格着色的四个分数 `sc`。
- 整栋汇总 `calcAll()`：窗面积、得热、损失**相加**；过热频率按房间面积加权平均；采光系数按立面长度加权平均。**这条汇总规则就是本轮"立面段汇总回立面"要沿用的规则。**
- 三个暴露度在网格里的定义（`gridConditions`）：采光 = `DF`；冬季得热 = `Qgain / 房间面积`；夏季过热 = `hotPer`。房间面积 = 立面长 × 进深 × 层数。
- 平面坐标：x 向东、y 向南，四条边的绘制方向为 南墙西→东、东墙南→北、北墙东→西、西墙北→南（从室外看每面墙都是**从左到右**）。本轮窗户的"沿墙位置"就用这个方向，与现有平面图一致。
- 关键性质（决定兼容性）：`calc(k)` 里所有量对"立面长度"都是**成比例**的——窗面积、玻璃面积、房间面积、传热系数、热容、内部得热全部 ∝ 长度。所以把一面墙切成 n 段完全相同的段，每段的采光、单位面积得热、过热频率都与整面墙**相同**；相加后又回到整面墙的数字。这是"从 V06 默认方案生成窗户"能对上 V06 的数学根据（§5）。

## 2. 窗户数据模型

### 2.1 一份可序列化的对象（JSON 形状）

```json
{
  "schema": "arch540/zoning-model",
  "version": 1,
  "units": "m, degrees, kWh",

  "box":   { "L": 20, "W": 12, "H": 3.0, "floors": 1 },
  "site":  { "climate": "apNow", "rotation": 0 },

  "walls": [
    { "id": "S", "index": 0, "baseAz": 180, "length": 20, "overhang": 0 },
    { "id": "E", "index": 1, "baseAz":  90, "length": 12, "overhang": 0 },
    { "id": "N", "index": 2, "baseAz":   0, "length": 20, "overhang": 0 },
    { "id": "W", "index": 3, "baseAz": 270, "length": 12, "overhang": 0 }
  ],

  "windows": [
    { "id": "S1", "wall": "S", "u": 1.25, "w": 2.50, "h": 1.80, "sill": 0.60,
      "floor": null, "overhang": null, "source": null }
  ],

  "room":     { "depth": 5 },
  "cooling":  { "mass": "mid", "vent": "win" },
  "assumptions": { "Gt": 67.9, "Ug": 0.60, "Uf": 0.80, "psig": 0.035, "fw": 0.11, "g": 0.50, "vt": 0.65,
                   "Uwall": 0.12, "psiI": 0.04, "obs": 15, "qint": 2.1, "nHyg": 0.3, "etaHR": 0.75 }
}
```

| 字段 | 含义 | 说明 |
|---|---|---|
| `box.L / W` | 南北向立面的宽 / 东西向立面的宽 | 与 V06 的"长度 / 进深"两个滑块相同 |
| `box.H` | 层高 | |
| `box.floors` | 层数 | **本轮语义与 V06 相同**：窗户描述一个标准层，按层数重复。分支默认 1 层（一层住宅）；保留滑块是为了能在 3 层下与 V06 默认方案比对（决定项 8） |
| `site.rotation` | 朝向偏转，度 | 与 V06 滑块相同：0 正南，正值偏西 |
| `walls[]` | 四段外墙 | **由 box 生成，本轮不可单独编辑**。`baseAz` 是未旋转时的朝向；实际朝向 = `norm(baseAz + rotation)`。`index` 是绕平面逆时针的顺序（南→东→北→西），也就是 V06 平面图边线的绘制顺序 |
| `walls[].overhang` | 挑檐深度 | 本轮**按墙**设置（与 V06 相同）。窗户级的 `overhang: null` 表示"跟随所在墙"，为以后每扇窗单独出挑预留（决定项 7） |
| `windows[].u` | 沿墙位置：窗**左边缘**到墙段起点的距离 | 起点 = 从室外看这面墙的**左端**（南墙的西端、东墙的南端、北墙的东端、西墙的北端），与 V06 平面图一致 |
| `windows[].w / h / sill` | 宽、高、窗台高 | 窗头高 = `sill + h`，不单独存 |
| `windows[].floor` | 所在层 | **预留**，本轮恒为 `null`（= 每层都有） |
| `windows[].source` | 来源 | **预留**：Rhino 导入时放 `{ "rhinoId": "...", "layer": "..." }`，手工建的为 `null` |
| `windows[].id` | 内部键 | **界面上不显示编号**（决定项 12）：报错和详情用"南墙从左数第 2 扇"指窗。内部仍保留一个不显示的稳定键（建后不变、删了不复用），用于记住选中状态和段的归属；Rhino 导入后由 `source.rhinoId` 接替 |

坐标系只有一个：窗户全部在**墙自身坐标**里（沿墙距离 + 高度），所以旋转体块时窗户不需要改任何数字，自然跟着转（§4 第 5 点）。

页面里的 `MODEL` 就是这个对象；界面状态（选中了哪段、显示哪个暴露度层）另放在 `UI` 里，不进 `MODEL`。`JSON.stringify(MODEL)` 即可导出；以后导入 = 替换 `MODEL` 后重画。

### 2.2 立面段（计算结果，不存入 MODEL）

```json
{ "id": "seg:S1", "wall": "S", "u0": 0, "u1": 5, "length": 5, "az": 180,
  "windows": ["S1"], "Aw": 4.5, "Ag": 3.4, "wwr": 0.30,
  "perimeterU0": 0,
  "result": { "DF": 2.9, "Wx": 21.3, "Hx": 3.1, "ovh": 1.2, "netPer": 18, "...": "calcSegment 全部字段" } }
```

`id` 从窗户编号派生（一段一窗时 `seg:S1`，无窗段 `seg:S-blank`），编辑窗户后同一扇窗的段还是同一个 id。`perimeterU0` 是这段起点绕整个周边的累计距离（南墙起点为 0），为以后布局阶段判断相邻和转角预留。

时间分布（"几月几点过热"）本轮**不记录**（决定项 15），留给建议层那一轮：到时在 `simulateHours` 循环里加三张"月 × 钟点"的表即可，不改任何现有数字。

### 2.4 这份结构以后如何对应 Rhino 导入

V08 的 `rhino/windows.json` 已经是"一面墙 + 若干具体窗"的形状：`windows[] = { id, floor, x, width, sill, height }`，`x` 是窗左边缘到立面左端的距离。对应关系是逐字段的：

| V08 `windows.json` | 本模型 | 备注 |
|---|---|---|
| `orientation: "S"` | `windows[].wall` | 一个文件一面墙 → 四个文件或一个多墙文件 |
| `facade.width / floor_height / floors` | `walls[].length`、`box.H`、`box.floors` | |
| `windows[].x` | `u` | 同一约定：左边缘、从室外看的左端起 |
| `windows[].width / height / sill` | `w / h / sill` | |
| `windows[].floor` | `floor` | 本轮 `null`；有逐层窗时再定义层的语义 |

## 3. 立面段的划分、暴露度、汇总

### 3.1 划分规则（决定项 3，已确认：B · 窗段与空墙段交替）

把一面墙上的窗按 `u` 排序，**每扇窗自己是一段**（`u … u+w`），**窗与窗之间、窗与墙端之间的空墙各是一段**。相接的两窗之间没有空墙段（长度 0 的段不生成）。没有窗的墙 = 一整段空墙段。

```
南墙 20 m，两扇窗 (u 2–5)、(u 12–15)
|--空--|[窗]|------空------|[窗]|--空--|
0      2    5             12   15     20
 空 2   窗 3     空 7        窗 3   空 5
```

段的类型写在结果里（`kind: "window" | "blank"`）。窗段的窗墙比 = 窗高 ÷ 层高（整段宽度都是窗），空墙段的采光、得热、透入辐射都为 0。

**这样切的后果**（已向用户说明）：把一面墙切成这样的段之后，**段的过热频率不能平均回立面**——一个"只有窗宽的小房间"过热远高于整面墙一间大房间，逐小时模拟对窗面积是非线性的。所以立面级指标不由段汇总得出，而是**引擎对整面墙连同它的全部窗单独算一次**（§3.3）。段级数值只用于分区和段详情。

被放弃的 A（中点切分、每窗一段、无缝）的优点是段值可以严格平均回立面；用户选 B 是因为它更贴近"窗在哪、墙在哪"，房间以后跨段布置。

### 3.2 每段的暴露度

每段用 `calcSegment` 算——它就是 V06 的 `calc(k)`，只是"墙长 = 段长、窗 = 这段上的窗（窗段一扇、空墙段零扇）、方位角 = 所在墙的方位角、挑檐 = 所在墙的挑檐"。得到与 V06 立面结果同名的全部字段。界面重点显示三个暴露度，定义与 V06 网格一致：

| 暴露度 | 引擎字段 | 单位 | V06 里的出处 |
|---|---|---|---|
| 采光 | `DF` | 采光系数 % | 表格"采光系数"列、网格 DF 层 |
| 冬季得热 | `Wx = Qgain / zoneA` | kWh/(m² 房间·年) | 网格 Wx 层 |
| 夏季过热 | `Hx = hotPer` | kWh/(m² 房间·年) | 网格 Hx 层、详情"高温时段透入辐射" |

详情面板另列：过热频率 `ovh`、净得热 `netPer`、热损失 `Qloss`、窗面积、玻璃面积、窗墙比，方便与 V06 对照。

### 3.3 立面级指标：整墙一次计算 + 段的加和核对

**立面级指标 = `calcSegment(整面墙, 该墙全部窗)`**。`calcSegment` 接受窗数组，整面墙连同它的所有窗当作一个房间模拟——这与 V06 的 `calc(k)` 是同一件事（V06 的 n 扇等大窗就是这个数组的特例）。所以只要窗是等大均匀的，立面级全部字段与 V06 相等，包括过热频率；窗不等大时，线性量（面积、得热、损失、采光）仍与"同样总窗面积"的 V06 相等，过热频率是"整面墙一间房"的值。

段的加和作为**核对**（自检项），下表列出哪些量段加和后必须等于整墙值：

| V06 立面字段 | 段 → 整墙的核对方法 | 是否必须相等 |
|---|---|---|
| `AwT, AgT, PT, totW, n, zoneA, Htr, Qgain, Qloss, net, Qsum, Qhot` | **相加** | 相等（只差浮点加法顺序） |
| `wwrAct` | ΣAwT ÷ (墙长 × H × 层数) | 相等 |
| `Uw`、`frameFrac` | 按窗面积加权 | 相等 |
| `netPer` | Σnet ÷ ΣAwT | 相等 |
| `hotPer, sumPer, lossPer` | ΣQ ÷ ΣzoneA | 相等 |
| `DF` | 按**段长**加权平均 | 相等（推导：DF ∝ 每米墙的玻璃面积，长度加权后恰等于整墙的每米玻璃面积） |
| `ovh, h25, TmaxIn` | **不核对**：段按面积平均 ≠ 整墙模拟（非线性，§3.1）。段详情显示段值，表格显示整墙值，并在方法说明里写明两者含义不同 | 不相等，属预期 |
| `wi, hw, sill, head, gap, uni, cover, theta` | 整墙计算直接给出（多窗不等大时 `wi` 显示范围） | — |
| `clamped`、`has` | `clamped` 不再存在（改为校验 V3）；`has` = 墙上有窗 | — |

整栋汇总 `_`（整体窗墙比、平均采光、净得失、过热频率、体形系数）= V06 `calcAll()` 的公式逐字复制，输入是四面墙的整墙结果。

- **列表编辑（主要方式）**：每面墙一个标签页（沿用 V06 的标签页），滑块下方是这面墙的窗户表，按 `u` 从左到右排列（与平面图上从室外看的顺序一致），每行："第 n 扇"、位置、宽、高、窗台 四个数字输入框（步进 0.05 m；高与窗台带上下限并注明允许范围，决定项 5）、删除按钮。改任何数字 → 立刻校验、重算、重画（与 V06 拖滑块的即时反馈相同）。

- **校验提示**：列表下方红字，每条一行、用"南墙第 2 扇"指窗；有错的输入框红框、有错的窗在平面上画红；该墙的段色带变灰并写「待修正」。**不会自动改任何值**。
- **「从 Version_06 默认方案生成窗户」**：按钮在体块面板下方。按下后把体块、窗台 / 窗头、四面墙的 `{wwr, n, oh}` 全部设回 V06 默认值（20 × 12 m、3 层、3.0 m、正南；南 40%/4、东 20%/2、北 15%/2、西 30%/2，挑檐 0；窗台 0.6、窗头 2.4），再对每面墙跑生成器。会覆盖手工编辑，先确认一次（决定项 14）。分支页面**打开时的默认状态就是这个**，所以一打开即可与 V06 并排对照。
- **不做拖拽**（决定项 9，已确认）：平面上拖窗要处理吸附、越界、重叠的实时反馈，而"不悄悄修正"意味着拖到非法位置只能报错，体验反而差；数字输入更精确，也更接近以后 Rhino 导入的"数据进来"方式。

## 5. 兼容性验证方法

### 5.1 引擎级：共享引擎 = V06 计算

1. 在 V06 页面（不改文件）以 `?test=1` 打开，取 `window.__digest`：6 组（3 气候 × 2 预设）× 4 立面的全部 `calc()` 数值 + 整栋 `_`。V06 已有此功能，SHA-256 前 16 位 `d4e82395b2e0eb5e`（PLAN_v06 记录）。

3. 逐字段比对：相对误差 ≤ 1e-9 记为相同。**不做逐字符比对**，因为求和顺序不同，最后一两位小数可能不同——报告最大相对差。

### 5.3 预计会变的数值、原因和幅度

| 情形 | 会变的量 | 原因 | 预计幅度 |

## 6. 后续阶段会对本轮提出的要求（只列要求，本轮不实现）

### 6.1 Rhino 导入
- **墙不再恒为四段矩形**：导入的体块可能是 L 形、五边形。要求：本轮除"从矩形生成 walls"这一个函数外，**所有代码都遍历 `MODEL.walls` 数组**，不写死 `S/E/N/W` 四个键（V06 的 `KEYS` 只保留在矩形生成器里）。方位角、长度、挑檐都从 `walls[i]` 读。
- **墙的方向约定要写进文档**：Rhino 侧外墙轮廓取逆时针（外法线向外），每段墙"从室外看的左端"即轮廓方向上的起点，与本轮 `u` 一致。写进 `ENGINE.md`。
- **`source` 字段**：窗和墙都留 `source`，导入后可以回溯到 Rhino 对象；工具自己的 `id` 与 Rhino 的编号分开。
- **层数与 Rhino 体块联动**（决定项 8）：`box.floors` 和 `box.H` 由 Rhino 体块的高度 / 层数给出，导入后页面的层数滑块显示导入值并可改（改了就与 Rhino 不一致，页面要提示）。**逐层窗**：Rhino 给的是每层各自的窗，本轮的"标准层 × 层数"语义要能切换为"逐层"。要求：`floor` 字段已预留；引擎 `calcSegment` 目前用 `floors` 做乘数，以后改为按 `floor` 分组各算——接口不变。
- **单位**：Rhino 文档可能是毫米。要求：导入函数负责换算，`MODEL` 内部恒为米，`units` 字段写明。

### 6.2 房间规格配置
- 房间类型（客厅、卧室、厨卫…）的最小面积、最小宽度、是否必须有窗、采光要求等放**配置文件**（形如 `rooms-config.js`），计算代码只读字段、不写房间名——与 `zoning-config.js` 同一原则。规范数值那时要逐条标注来源（BC Building Code / BC Housing 指南），未核对的标为假设。
- 要求本轮：每个立面段输出的字段要**够用**——长度、窗面积、玻璃面积、窗墙比、`DF / Wx / Hx / ovh`、绕周边的位置 `perimeterU0`、所属墙。这些本轮都已在 §2.2 里。
- 段级的**平面网格**：V06 的 `gridConditions` 按四个立面分配格子条件；房间阶段需要按**段**分配（每段只影响自己正对的那片进深）。要求：引擎里的 `kernelCell / sunPatch` 已是"按一个光源"写的，以后只需给 `gridConditions` 换输入（光源列表 = 段列表，各带 `u0, u1`），核心公式不变。本轮不改它，但接口设计时不要让它依赖 `KEYS`。

### 6.3 布局生成
- 需要段的**顺序与相邻关系**（哪两段在转角相遇）→ 本轮的 `walls[].index` 和 `perimeterU0` 已给出，转角 = 前一墙末段与后一墙首段。
- 需要**稳定的段编号**，编辑一扇窗后能说"这段还是那段" → 本轮 `seg:<窗编号>`。
- 需要"多窗合一段"的可能（两扇近窗服务同一个房间）→ 本轮 `calcSegment` 接受窗**数组**，切分规则集中在一个函数里，以后加"合并阈值"不动引擎。
- 需要每段的**进深方向**信息（房间能多深）→ 现有 `room.depth` 全局；以后可能按段给。字段位置预留在段结果里（`depth` 现在取全局）。

### 6.4 旋转稳定性
- 分区随旋转更新时，若分配是"取最高分"，会在某些角度**跳变**。V06 用"领先幅度"（`margin`）显示"多种可能"。要求本轮：暴露度对旋转角**连续**（引擎的 `interpN` 是线性插值、模拟逐小时——都连续；已满足），并在自检里加一个**旋转扫描**工具函数 `sweepRotation(step)`：0–90° 每步算一次各段暴露度，输出表格，供以后检查跳变。本轮只做函数和数据，不做图。
- 旋转不改窗的 `u`（§2.1）—— 这是稳定性的前提，本轮已满足。

### 6.5 建议层：把仿真结果翻译成决策语言（最终定位的核心）

**分工原则**：引擎负责一切数字，LLM 负责语言和排序。LLM 不许引用事实表以外的任何数字，也不许自己算。

```
MODEL ──引擎──▶ 事实表 facts.json ──LLM──▶ 决策语言 + 排好序的建议 ──点「采纳」──▶ 改 MODEL ──引擎重算
                     ▲                                │
                     └────── 每条建议附带的改动，先由引擎试算出"预计效果" ──┘
```

- **事实表**（引擎输出，纯数据）：每段的暴露度、窗墙比、窗尺寸、时间分布的摘要（哪几个月、哪几个钟点占比多少；建议层那一轮再在 `simulateHours` 里记录，本轮不做）、与该段目标房间要求的差距（房间阶段之后才有）、以及引擎**已经试算过**的几种改法和效果（V06 的三条规则就是试算器：窗墙比 ±5%、挑檐 +0.4 m、缩到 12%）。
- **建议 = 对 MODEL 的一个具体改动**：`{ "target": "S2", "change": { "w": 1.8 }, "why": "…", "effect": { "ovh": [5.5, 2.1], "DF": [2.9, 2.4] } }`。`target` 是窗编号或墙编号，`change` 是能直接写进 `MODEL` 的字段。这样"采纳"就是一次赋值 + 重算，与 V06 的 `adoptAdvice` 同一机制。LLM 只能从事实表里**已试算**的改法中挑选和组合，写不出引擎没算过的效果。
- **兜底**：V06 现有的三条规则式建议保留，不联网或没有密钥时照常工作；LLM 版是在它之上的"翻译 + 排序 + 综合"层。
- **能说与不能说**：引擎有时间分布的量才能说"几月几点"——室温超 25 °C、透入的直射辐射、最高室温三项本轮预留（§2.2）。**眩光目前没有指标**，V06 的采光系数是全阴天平均值，与眩光无关；要说"眩光"必须先在某一轮新增一个指标（例如低太阳高度角时直射光进入房间的小时数），并注明是简化假设。在那之前，工具不说"眩光"。
- **对本轮的要求**：① `calcSegment` 无副作用（§6.6），这样试算多种改法可以批量跑；② 事实表的字段名与段结果一致，不另起名；③ 段结果对象留出 `hourly` 位置（本轮为 `null`），建议层那一轮填三张"月 × 钟点"表。
- **接入路线**（决定项 16：本轮不实现，路线未定）：LLM 怎么接入。工具目前是双击打开、不联网的单文件。可选：a. 页面直接调 Claude API（需要用户自己填密钥、联网、按用量计费，密钥只存浏览器本地）；b. 经过 V07 那种本地小服务转发（密钥放在本机文件，不进页面）；c. 本地模型（不联网，但要装软件、语言质量差一档）；d. 先用规则式建议 + 事实表导出，LLM 那层等以后再接。我的推荐是 **b**：与 Rhino 链路共用同一个本地服务，密钥不进页面。到建议层那一轮再定。

### 6.6 通用
- **`MODEL` 是唯一真值**：导入 = 替换 `MODEL`；导出 = 序列化 `MODEL`；撤销（以后）= 保存 `MODEL` 快照。界面状态一律不进 `MODEL`。
- **引擎无副作用**：`calcSegment` 不读全局。V06 的 `calc()` 读 `S`，本轮改掉这一点后，以后批量试算（布局搜索）才能并行、可缓存。
- 气候数据**独立成文件**：以后加站点或换年份只换 `wwr-climate.js`。
