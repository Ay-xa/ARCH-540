## 1. 项目现状与接入方式

### 1.1 现状

- 工具是单个文件 `Version_02/wwr-tool.html`（718 行，其中第 200–260 行是脚本注入的气候数据，包含三组 8760 小时序列，占文件体积的 90%）。界面、计算、平面图、剖面图都在这一个文件里。
- 建筑是一个 L × W 的矩形（L = 南北立面宽，W = 东西立面宽），四个立面 S / E / N / W。每个立面后面有一条进深为 D（房间进深滑块，默认 5 m）的"房间带"。
- `calc(k)` 对每个立面算出四个维度，全部是**该房间带的平均值或总量**，没有空间分布：
  - `DF`：房间平均采光系数 %（BRE 公式，全阴天），`limit = 2.5 × 窗头高` 是有效采光进深。
  - `Qgain`：采暖季太阳得热 kWh/a（该立面全部楼层）；`dW`、`pW`、`shW` 是冬季直射占比、直射剖面角、挑檐遮挡比。
  - `Qhot` / `hotPer`：高温时段（室外 > 22 °C）透入辐射 kWh/a 与按房间面积折算值 kWh/m²·a；`dH`、`pH`、`shH` 同上。
  - `ovh`：逐小时单节点模拟得到的室内 > 25 °C 小时占比。
  - `zoneA = len × D × floors` 是房间带面积。
- 平面图 `renderPlan()`：建筑矩形画在一个 `<g transform="rotate(rot)">` 里，朝向偏转靠整组旋转；四个立面边线的坐标在建筑自身坐标系里固定（南在下、北在上、东在右、西在左）。
- 朝向偏转滑块步长 5°，`facAz(k) = 固定方位 + rot`，所有辐射数组按方位角插值。
- 一次完整渲染约 11 ms（主要是四次 8760 小时模拟）。

### 1.2 新功能如何接入

- 新功能**只读** `calcAll()` 的结果（每个立面的 DF、Qgain、Qhot、dW/pW/shW、dH/pH/shH、zoneA、ovh 等），不改 `calc()`、`simulateHours()`、`calcAll()` 的任何一行。
- 网格、适合度、分区、建议四块各自是独立的函数组，挂在 `render()` 末尾，输出到平面图上新增的一个图层和几个新界面区块。
- 修改后，原有表格、摘要、设计提示、详情面板的所有数值应与修改前逐位一致。验证方法见 §9。

## 3. 网格采光的空间分布模型

### 3.1 网格

- 楼层平面（建筑自身坐标系，南下北上）划成边长 g 的正方格，默认 g = 1 m，可在 0.5–2 m 之间调（决定项 11）。L = 20、W = 12 时 240 格；g = 0.5 时 960 格。
- 每格用中心点计算。格子到四个立面的垂直距离记为 d_S、d_E、d_N、d_W（m）。
- 只算一个标准层：所有输入值都已是"每平方米房间面积"的量（`Qgain / zoneA` 等），与层数无关。

### 3.2 单个立面的采光衰减曲线

符号：DF_k = 现有模型算出的立面 k 房间平均采光系数（%）；D = 房间进深（m）；h = 窗头高度（m）；d = 格子到立面 k 的距离（m）。

一个格子从立面 k 得到的采光系数：

```
DF_k(d) = DF_k × φ(d)
φ(d) = exp(−d/λ) × (D/λ) / (1 − exp(−D/λ))      0 ≤ d ≤ D
φ(d) = 0                                           d > D
λ = 1.0 × h（衰减长度，m）
```

- φ 是归一化的衰减曲线：它在 0 到 D 上的平均值恰好等于 1，所以**该立面房间带内格子的平均值 = DF_k，由公式保证**（连续情况下完全相等；用格子中心离散化后误差约 (g/λ)²/24，g = 1、λ = 2.4 时 < 1%）。
- 取值举例：h = 2.4、D = 5 时 φ(0) = 2.38，φ(5) = 0.30。若房间平均 DF 为 3.5%，则靠窗处约 8.3%，房间最里约 1.0%。这与侧窗采光房间的典型剖面（靠窗处高、进深处降到十分之一左右）一致。
- λ = 1.0 × 窗头高是**假设值**（决定项 4）：侧窗采光的经验是采光系数大致每隔一个窗头高度衰减到约三分之一，从 1 m 到 6 m 大约降一个数量级，对应 λ ≈ 2.2–2.5 m。做成可调常数，写在代码注释里。
- 沿立面方向不做变化（整条立面视为均匀光源，与现有 DF 按"每米立面"计算的做法一致）。窗与窗之间的暗区（现有 `uni` 指标）本阶段不映射到网格，作为已知简化。
- d > D 处为 0：房间带以外没有这个立面的光。这与现有模型"房间进深 D 处有内墙"一致（决定项 3）。

### 3.3 多个立面叠加与转角

一个格子的采光系数 = 四个立面贡献之和：

```
DF(c) = Σ_k DF_k(d_k(c))
```

采光系数对不同窗口是线性可加的，所以直接求和是物理上正确的。转角格子同时在两条房间带内，得到两个立面的光，自然高于同一立面中段、离窗相同距离的格子，只要相邻立面有窗。

### 3.4 与现有工具的一致性目标

- **分量一致性**：立面 k 房间带内，"来自立面 k 的分量"的平均值与 DF_k 的偏差 ≤ 2%（离散化误差）。
- **总量一致性**：立面 k 的"中段"（房间带内、且离两个侧立面的距离都 > D 的格子）总采光平均值与 DF_k 的偏差 ≤ 10%。中段只可能混入对面立面的光，而对面立面的光只有在 D > W/2（或 L/2）时才到得了，默认方案下偏差应为 0。
- 转角部分的总量必然高于 DF_k，这是设计意义上的真实情况，不作为误差。

## 4. 冬季得热暴露与夏季过热暴露的分配

两者用同一种分布曲线，只是输入的辐射量和太阳角度不同。

### 4.1 每个立面的输入量（全部来自现有 `calc()` 结果）

| 量 | 来源 | 单位 |
|---|---|---|
| 冬季得热强度 gainPer_k | `Qgain / zoneA` | kWh/(m² 房间面积·a) |
| 冬季直射占比（挑檐后）dirW_k | `dW × (1 − shW) / fsW` | – |
| 冬季直射剖面角 pW_k | `pW` | ° |
| 夏季过热强度 hotPer_k | `hotPer`（= `Qhot / zoneA`） | kWh/(m²·a) |
| 高温时段直射占比 dirH_k | `dH × (1 − shH) / fsH` | – |
| 高温时段剖面角 pH_k | `pH` | ° |

冬季用"太阳得热"（不扣窗户热损失）：分区关心的是哪里晒得到冬天的太阳；窗户热损失是立面属性，不随位置变化。

### 4.2 分布曲线

太阳光进窗后分两部分：直射光照在地面上一块条带里，散射光像采光一样随距离衰减。再考虑室内空气会混合，一部分热量均匀摊到整个房间带：

```
κ(d) = mix × 1 + (1 − mix) × [ dir × U(d) + (1 − dir) × φ(d) ]

U(d) = D / (d₂ − d₁)   当 d₁ ≤ d ≤ d₂，否则 0
d₁ = sill / tan(p)，d₂ = min(D, head / tan(p))      直射光照到地面的范围
若 d₁ ≥ D（太阳太高或房间太浅），直射部分改用 φ(d)
mix = 0.5（空气混合比例，假设值，决定项 5）
```

- 三项（均匀 1、U、φ）在 0 到 D 上的平均值都是 1，所以 κ 的平均值也是 1，**房间带内的分量平均值恰好等于 gainPer_k 或 hotPer_k**。
- 每格的暴露值：
  ```
  冬季得热暴露 Wx(c) = Σ_k gainPer_k × κ_W,k(d_k(c))     kWh/(m²·a)
  夏季过热暴露 Hx(c) = Σ_k hotPer_k  × κ_H,k(d_k(c))     kWh/(m²·a)
  ```
- 角度差异带来的设计含义：冬季南向剖面角约 30°，直射光照到 1.0–4.2 m 深处（窗台 0.6、窗头 2.4 时）；高温时段南向剖面角约 57°，只照到 0.4–1.6 m。所以冬季得热分布得深，夏季过热集中在窗边。西向高温时段剖面角约 45°，照到 0.6–2.4 m，比南向深。
- 默认方案下的量级（按现有表格估算，实施时以实际计算为准）：冬季得热强度南约 30、西约 17、东约 10、北约 3 kWh/m²·a；夏季过热强度（机场站当下）南 4.9、西 4.3、东 1.0、北 0.7，2080 年南 29、西 23。

### 4.3 热力图

- 三个图层各用一种颜色由浅到深：采光用 `--day`，冬季得热用 `--sun`，夏季过热用 `--heat`，透明度按值线性映射到当前图层的 0 到最大值。图例显示最大值和单位。
- 格子画在平面图已有的旋转组里，所以随朝向偏转一起转；格子的值本身也随偏转变化（因为每个立面的 DF、Qgain、Qhot 都随方位角变化）。

## 5. 功能配置表

### 5.1 文件形式（决定项 2）

独立文件 `Version_03/zoning-config.js`，内容是一个 JS 对象赋值：

```js
window.ZONING_CONFIG = { ... };
```

用 `<script src="zoning-config.js">` 引入。不用 JSON 文件，因为双击打开的网页（file:// 协议）不能用 `fetch()` 读本地 JSON（地块地图工具 V03 就是因此失败过）。切换用途 = 换这个文件（或在文件里改 `use` 字段）。文件缺失时页面顶部显示一行提示，其余功能照常。

### 5.2 结构

```js
window.ZONING_CONFIG = {
  use: 'apartment', label: '公寓（整层一个大户型）',
  version: 1,
  grid: 1.0,                       // 默认网格尺寸 m，可被侧栏滑块覆盖
  smoothRadius: 1.5,               // 分数空间平滑半径 m（§7）
  contiguity: 15,                  // 连片强度 β，分（§7）
  minRegion: 4,                    // 最小成片面积 m²（§7）
  functions: [
    { key: 'living', label: '客厅', color: '--sun',
      daylight: { dir: 'up',   lo: 1.0, hi: 3.0, w: 1.0 },   // 采光系数 %
      winter:   { dir: 'up',   lo: 5,   hi: 25,  w: 0.7 },   // 冬季得热暴露 kWh/m²·a
      overheat: { dir: 'down', lo: 5,   hi: 20,  w: 0.4 },   // 夏季过热暴露 kWh/m²·a
      area: { min: 0.30, max: 0.45 },                        // 面积占比
      adjacency: [],                                         // 预留：[{to:'bedroom', w:0.5}]
      note: '...' },
    { key: 'bedroom', label: '卧室', color: '--cold', ... },
    { key: 'service', label: '服务区', color: '--slab', ... }
  ]
};
```

- 每个条件有 `dir`（up = 越高越好，down = 越低越好）、`lo` / `hi`（分数从 0 升到 100 或从 100 降到 0 的区间，物理单位）、`w`（权重）。
- `adjacency` 本阶段只预留字段，不参与计算。
- 计算代码只按 `functions` 数组和三个条件键循环，不写任何功能名称，功能数量不限。

### 5.3 公寓表默认值与理由

| 功能 | 采光 DF % | 冬季得热 kWh/m²·a | 夏季过热 kWh/m²·a | 面积占比 |
|---|---|---|---|---|
| 客厅 | up，1.0 → 3.0，w 1.0 | up，5 → 25，w 0.7 | down，5 → 20，w 0.4 | 0.30–0.45 |
| 卧室 | up，0.7 → 2.0，w 0.7 | up，0 → 20，w 0.3 | down，2 → 10，w 1.0 | 0.30–0.45 |
| 服务区 | down，0.5 → 2.5，w 1.0 | down，0 → 20，w 0.4 | up，0 → 10，w 0.2 | 0.20–0.35 |

理由（标注来源层级）：

- **采光阈值**：常见的采光系数经验分级是 < 2% 偏暗、2–5% 良好、> 5% 明亮（BRE / CIBSE 采光指南中的常用分级，此处按公开资料的一般说法，未逐条核对版本）。客厅要到 3% 才满分；卧室 2% 即满分（卧室不需要很亮）；服务区在 0.5% 以下满分、2.5% 以上零分（不该占用亮的位置）。
- **冬季得热**：区间按默认方案的量级（南向房间带约 30，北向约 3）设定，让南向满分、北向接近零分。客厅权重高，卧室权重低（卧室白天少用），服务区反向低权重（别占晒得到的位置）。这些是**设计判断，不是规范值**。
- **夏季过热**：卧室最怕夜间过热，权重 1.0、容忍度最低（2 → 10）：机场站当下东向 1.0 满分、西向 4.3 得约 70 分、南向 4.9 约 65 分；2080 年西向 23 零分。客厅容忍度较高（5 → 20），白天使用、可以主动遮阳；服务区反向（愿意承担热的位置，做缓冲）。区间取值是设计判断。
- **面积占比**：大户型公寓客厅 + 餐厅 + 厨房约 30–45%，卧室合计 30–45%，卫生间、储藏、走道、交通核 20–35%。**估计值**，无规范依据；下限之和 0.80 ≤ 1 ≤ 上限之和 1.25，保证有解。
- 决定项 7：以上数值请确认或改动。

## 6. 适合度分数

对每格 c、每种功能 f：

```
每个条件的分数：s_i = 100 × r(v_i; lo_i, hi_i)         dir = up
                s_i = 100 × (1 − r(v_i; lo_i, hi_i))   dir = down
r(v; lo, hi) = t² (3 − 2t)，t = clamp((v − lo)/(hi − lo), 0, 1)   平滑斜坡

总分 S_f(c) = Σ_i w_i s_i / Σ_i w_i         0–100
```

- 三个条件 v_i 就是阶段 A 的 DF(c)、Wx(c)、Hx(c)。分数只依赖格子自身的条件，**不使用朝向、立面名称或任何硬性方位规则**；东向比西向更适合卧室，是因为东向格子的夏季过热暴露更低，而不是因为它叫东。
- 平滑斜坡而不是折线，是为了让分数对输入连续可导，减少分区边界的抖动。

## 7. 分区分配算法

### 7.1 步骤

1. **空间平滑**：每格的每个功能分数取半径 `smoothRadius`（默认 1.5 m，与网格尺寸无关）范围内格子的平均值，得到 S̃_f(c)。目的：去掉单格噪声，避免棋盘状。
2. **面积平衡（水位法）**：每种功能有一个偏置 λ_f（初始 0）。每格暂定为 `argmax_f (S̃_f + λ_f)`。统计各功能面积占比：低于下限的功能 λ_f 增加一步，高于上限的减少一步；步长从 5 分开始，方向反转时减半；直到全部落在区间内（容差 1 格）或步长 < 0.1 分。因为提高 λ_f 只会让 f 的面积单调增加，在"下限之和 ≤ 1 ≤ 上限之和"时必有解。
3. **连片平滑（Potts 模型，ICM 迭代）**：每格的"代价" = (100 − S̃_f − λ_f) + β × (四邻中标签不同的格数)，β = `contiguity`（默认 15 分）。按固定顺序逐格改成代价最小的功能，最多 8 轮，直到没有格子改变。β 的含义：一个格子要"孤立"于邻居，它的分数优势至少要超过 β × 邻居数才值得。
4. **小块清理**：四连通成片面积小于 `minRegion`（默认 4 m²）的区域，并入与它共享边界最长的相邻功能。
5. **复核面积**：若第 3、4 步使某功能超出区间 2% 以上，微调 λ 后重复第 3–4 步，最多 5 次；仍超出则如实显示"面积约束未完全满足"。

### 7.2 如何保证连续成片

- 平滑（第 1 步）去掉噪声源；Potts 项（第 3 步）对每条"功能分界边"收取代价，所以边界会尽量短、区域尽量成块；小块清理（第 4 步）兜底。

### 7.3 如何保证结果稳定

- 全过程**没有随机数、没有历史依赖**：λ 每次从 0 重新求解，ICM 顺序固定，同样的输入一定得到同样的输出。不用"记住上一次分区"的做法，因为那会让结果依赖操作路径，无法复现，也会让"只改配置表"的验收失真。
- 分数对输入连续（平滑斜坡 + 空间平滑），λ 是分数分布的连续函数，所以输入微变时只有分界线附近、两种功能分数接近的格子会换标签。
- 无法完全排除的情况：两种功能在一整片区域分数几乎相等时，微小变化可能让整片翻转。由于分数随离窗距离连续变化，这种"平局"通常只沿一条线出现，不会覆盖一片。§9 的 40° → 50° 逐度扫描会实际测量并报告最大翻转比例；若超过目标（相邻两度之间改变功能的格子 ≤ 5%），再调 β 或加入"平局带"处理。
- 朝向偏转滑块目前步长 5°，扫描测试用 1° 步长在自检里以程序方式设置 `S.rot`。建议顺便把滑块步长改为 1°（决定项 8），不影响现有数值。

### 7.4 解释句的生成

对被分为功能 f 的格子，找分数第二高的功能 g，比较 f 与 g 的三个条件分数，取差值最大的条件作为"主因"，用模板拼句：

- 主因短语，例如：「采光 3.4%，足够客厅使用」「冬季得热 28 kWh/m²，晒得到冬天的太阳」「夏季过热暴露 1.2，比南侧 4.9 低得多」「采光只有 0.6%，不适合居住功能」。
- 若该格的原始最高分不是 f（被面积约束或连片调整改过），句尾加「；为满足面积占比 / 保持成片被划入{f}」。
- 例：「客厅 82 分（次选卧室 61 分）：冬季得热 28 kWh/m²，晒得到冬天的太阳；采光 3.4% 足够。」

### 建议规则（使用配置表阈值，不写死功能名之外的数值）

对每个有窗立面 k，取其房间带内的格子，统计主导功能 f*：

| 规则 | 触发条件 | 建议 |
|---|---|---|
| R1 卧室过热 | f* = 卧室，且该立面 hotPer 超过卧室过热区间的中点，或 ovh > 5% | 南向：挑檐加到 min(1.5, 现值 + 0.4)；东西向：窗墙比每次降 0.05，直到 hotPer 低于卧室区间下限或窗墙比 ≤ 0.15。给出修改后的预测值 |
| R2 客厅偏暗 | f* = 客厅，DF < 客厅采光区间上限，且窗户冬季净得热 > 0 | 窗墙比每次加 0.05，直到 DF 达标或过热频率超过 5% 或窗墙比 = 0.6 |
| R3 服务区大窗 | f* = 服务区，窗墙比 > 0.15，且冬季净得热 < 0 | 窗墙比降到 0.12（保留基本采光），给出热损失减少量 |
| R4 客厅过热 | f* = 客厅，ovh > 10% | 与现有设计提示相同的挑檐 / 遮阳建议，但附「采纳」 |

预测值通过 `calc(k, {wwr 或 oh})` 试算得到，与现有设计提示的做法相同。

## 11. 为以后的用途预留

切换用途只换配置表；计算代码按 `functions` 数组循环，功能数量和名称不限。加入办公室和社区中心时，预计需要补充的内容：

| 需求 | 配置表新增字段 | 是否需要改计算代码 |
|---|---|---|
| 办公室要求采光均匀 | `daylight.uniformity`（对邻域内 DF 变化幅度的容忍度） | 需加一个"邻域均匀度"条件的格子计算（一个小函数），评分代码不变 |
| 眩光 / 直射光 | `glare`（对直射光落点的容忍度） | 阶段 A 的曲线里已经分开算了直射部分 U(d)，只需把它单独输出为一个条件 |
| 较高内部得热 | `internalGain` W/m²（功能自身的发热） | 作为该功能过热条件的附加项（相当于降低容忍度），评分代码加一项 |
| 使用时段（白天 / 夜间） | `hours: 'day' | 'night'` | 需要数据管线把高温时段辐射按白天 / 傍晚拆分（改 `epw_to_clim.py` 和数据块），这是唯一牵涉 Python 脚本的项 |
| 相邻关系（社区中心的大厅靠入口、办公室的会议室靠工位） | 已预留 `adjacency: [{to, w}]` | 在 Potts 代价里加一项"与指定功能相邻得奖励"，分配算法加几行 |
| 最小房间尺寸 | `minRegion` 按功能分别设置 | 小块清理按功能取阈值 |
| 入口位置 | 顶层字段 `entrance: {facade, offset}` | 需要新的格子条件"到入口的距离" |

功能数量增加（办公室：开放工位、会议室、专注室、核心筒；社区中心：大厅、教室、咖啡、办公、核心筒）不需要改算法。

## 12. 已知简化（会写进代码注释和页面说明）

- 采光沿立面方向均匀，不体现窗间墙暗区。
- 冬季 / 夏季暴露只是太阳辐射的落点分布加一半空气混合，不是逐小时逐格的热模拟；房间内实际温差比辐射图显示的更平缓。
- 只算一个标准层，顶层屋面和底层地面的差别不体现在分区上。
- 面积占比、条件阈值、权重都是设计判断值，不是规范值。
- 分区只考虑采光与热环境，不考虑结构、管井、噪声、视野、私密性。
